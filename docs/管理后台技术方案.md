## 1. 目标与范围

### 1.1 要解决的问题

运营同事无需改动代码、无需发版，登录后台即可维护以下内容，改动实时生效到官网：

| 内容模块 | 官网位置 | 当前状态 | 后台能力 |
|---------|---------|---------|---------|
| 首页 Banner | 首页首屏轮播 | 硬编码在前端 | 增删改、上传图片、排序、上下架 |
| 新闻动态 | 新闻列表页 + 首页新闻区 | 硬编码（`EXTENDED_NEWS_LIST`） | 富文本编辑、封面图、草稿/发布、置顶 |
| 酒店名录 | 酒店名录页 | 硬编码（`HOTEL_DIRECTORY_LIST`） | 增删改、多图上传、区域/品牌筛选字段维护 |
| 留资线索 | 合作加盟页咨询表单 | 表单仅前端假提交，**数据未落库** | 线索列表、跟进状态流转、来源归因、新线索红点提醒、**企业微信群机器人即时推送** |
| 访问统计 | 全站页面 | 无统计 | PV/UV、环比、趋势图、热门页面、来源渠道 |
| AI 流量归因 | 全站页面 | 无统计 | AI 渠道 UV / 渗透率 / 线索转化、渠道分布环形图、入站明细 |

### 1.2 明确不做（本期范围外）

- 用户端注册 / 会员体系
- 在线预订 / 支付（保持现有跳转携程逻辑）
- 多语言管理
- 复杂工作流（多级审核），本期仅"草稿 / 发布"两态
- 品牌矩阵数据的后台化（品牌变动极少，保持代码维护；如有需要二期再加）
- 案例库管理、下载链接配置等与本站业务无关的模块

## 2. 总体架构

### 2.1 架构总览

```
┌─────────────────────────────────────────────────┐
│                  Sealos 应用启动器                │
│  ┌───────────────────────────────────────────┐  │
│  │         单容器（Node.js 服务）              │  │
│  │                                           │  │
│  │   /          → 官网前端静态文件（Vite 构建） │  │
│  │   /admin     → 管理后台静态文件             │  │
│  │   /api/*     → REST API                   │  │
│  │   /uploads/* → 已上传图片（持久卷）          │  │
│  │                                           │  │
│  └──────────────┬────────────────────────────┘  │
│                 │                               │
│        持久卷 /app/data                         │
│        ├── data.db（SQLite 单文件）             │
│        └── uploads/（banner/新闻/酒店图片）      │
└─────────────────────────────────────────────────┘
```

**核心决策：单容器 + SQLite + 持久卷。**

- 一个 Node.js 进程同时托管三个东西：官网静态文件、管理后台静态文件、API。
- 数据库用 SQLite（单文件 `data.db`），和图片一起放在持久卷上。
- Sealos 应用启动器部署 1 个实例、挂 1 个持久卷、配 1 个域名，即完成全部上线。

**为什么是单容器而不是前后端分开部署：**

- 内容量级小（几十条新闻、几百家酒店、几张 banner），没有高并发压力。
- 单容器省去跨域（CORS）、多域名证书、多应用编排的复杂度。
- 运维面最小：一个应用、一个卷、一份日志。
- 将来若流量上涨，前端静态文件可以随时拆到 CDN，API 独立扩容，架构不返工（见 §10 演进路径）。

### 2.2 技术选型

| 层 | 选型 | 理由 |
|---|------|------|
| 前端（官网） | 现有 Vite + React + TS + Tailwind，不改动栈 | 仅把硬编码数据改为运行时请求 API |
| 管理后台 UI | 同栈另建 Vite 应用（`admin/`），React + TS + Tailwind | 与官网视觉风格统一，无第三方后台框架学习成本 |
| 富文本编辑器 | wangEditor 5 | 中文友好、轻量、MIT 协议，适合新闻编辑 |
| 后端框架 | Node.js 22 + Fastify + TypeScript | 与前端同语言；性能好；自带 schema 校验生态 |
| 数据校验 | Zod | 请求体校验，前后端可共享类型 |
| 数据库 | SQLite（`better-sqlite3` 驱动） | 单文件、零服务、有事务；放在持久卷上即完成持久化 |
| ORM / SQL | Drizzle ORM | TS 优先、轻量、SQL 透明，迁移工具简单 |
| 鉴权 | 用户名密码 + JWT（httpOnly Cookie） + bcrypt | 后台用户仅个位数，无引入 OAuth/SSO 的必要 |
| 图片处理 | sharp | 上传时统一转 WebP、限制最大尺寸，控制体积 |
| 上传 | Fastify multipart | 类型 / 大小白名单校验 |

**关于"为什么不直接用 JSON 文件当数据库"**：多人同时保存会互相覆盖、无事务、无校验、无查询能力。SQLite 同样只是一个文件，运维成本与 JSON 完全一致，但避免了上述所有问题。

**关于"为什么不用 Sealos 的托管数据库（PostgreSQL/MySQL）"**：对本项目是杀鸡用牛刀——多一个计费服务、多一套连接管理。SQLite 足够支撑到日均万级访问。方案保留切换路径（见 §10）。

## 5. API 设计

### 5.1 公开接口（官网前端调用，无需鉴权，GET 支持 HTTP 缓存）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/banners` | 已上架 banner 列表（按 sort_order） |
| GET | `/api/news?page=&size=&category=` | 已发布新闻分页列表（不含正文） |
| GET | `/api/news/:id` | 新闻详情（含正文） |
| GET | `/api/hotels?region=&brand=&city=` | 已发布酒店列表（支持筛选） |
| POST | `/api/leads` | 提交咨询表单（Zod 校验 + 限流：每 IP 每分钟 3 次）；落库后异步推送企业微信群机器人（配置 `WECOM_WEBHOOK_URL` 时启用，推送失败不影响提交结果） |
| POST | `/api/track` | 页面访问上报（前端 sendBeacon，/admin 路径不上报） |

### 5.2 鉴权接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/login` | 登录，写 httpOnly Cookie（限流：每 IP 每分钟 5 次） |
| POST | `/api/auth/logout` | 登出 |
| GET | `/api/auth/me` | 当前登录用户信息（后台前端启动时校验会话） |

### 5.3 管理接口（均需鉴权，路径统一 `/api/admin/` 前缀）

| 资源 | 方法 | 路径 | 说明 |
|------|------|------|------|
| Banner | GET/POST | `/api/admin/banners` | 列表（含下架）/ 新建 |
| | PUT/DELETE | `/api/admin/banners/:id` | 编辑 / 删除 |
| | PUT | `/api/admin/banners/sort` | 批量保存排序 |
| 新闻 | GET/POST | `/api/admin/news` | 列表（全状态、可搜索）/ 新建 |
| | PUT/DELETE | `/api/admin/news/:id` | 编辑 / 删除 |
| | PUT | `/api/admin/news/:id/status` | 发布 / 转草稿 |
| 酒店 | GET/POST | `/api/admin/hotels` | 列表 / 新建 |
| | PUT/DELETE | `/api/admin/hotels/:id` | 编辑 / 删除 |
| 线索 | GET | `/api/admin/leads?status=&page=` | 线索列表（响应含待回访总数，用于红点徽标） |
| | PUT | `/api/admin/leads/:id/status` | 更新跟进状态（待回访 / 已联系） |
| | DELETE | `/api/admin/leads/:id` | 删除 |
| 统计 | GET | `/api/admin/stats/overview?range=7d\|30d` | PV/UV/线索转化 + 环比 + 趋势 + 热门页面 + 来源渠道 |
| AI 归因 | GET | `/api/admin/stats/ai?range=7d\|30d` | AI 渠道 UV、渗透率、AI 来源线索转化、渠道分布、入站明细 |
| 备份 | GET | `/api/admin/export` | 全站数据打包 JSON 下载（banner/新闻/酒店/线索/配置） |
| 上传 | POST | `/api/admin/upload` | 单图上传（multipart），返回路径；统一转 WebP，最长边 2400px，单张 ≤ 5MB |
| 账号 | PUT | `/api/admin/password` | 修改自己的密码 |

统一响应格式：`{ code: 0, data: ... }` / 错误 `{ code: xxx, message: "..." }`。

## 6. 管理后台功能清单

访问路径：`https://<域名>/admin`

| 页面 | 功能 |
|------|------|
| 登录页 | 用户名 + 密码；失败 5 次锁定 10 分钟；登录态 7 天 |
| 布局 | 左侧导航（线索 / 访问统计 / AI 归因 / Banner / 新闻 / 酒店 / 修改密码），顶栏显示当前账号 + **导出数据备份** + 退出 |
| 留资线索 | 表格列表（称呼/电话/表单类型/酒店名/留言/来源页/时间，支持状态筛选与搜索）；跟进状态下拉即改（待回访 ⇄ 已联系）；左侧导航「N 新」红点徽标（仅统计待回访）；删除二次确认 |
| 访问统计 | PV / UV / 线索转化三张指标卡（今日 vs 昨日环比）；近 7 天 / 近 30 天趋势图；热门页面 Top 10（显示中文可读名）；来源渠道 Top 8；/admin 自身访问不计入 |
| AI 流量归因 | 四张指标卡（AI 渠道 UV、AI 流量渗透率、AI 来源线索数、AI 线索转化率）；渠道分布环形图；入站明细表（AI 来源 / 落地页 / UV / 线索数）；内置 10+ AI 入口识别规则（豆包、DeepSeek、Kimi、通义、文心一言、ChatGPT、Perplexity、Copilot、QQ 浏览器 AI 等，按 referrer + UA 匹配，规则表代码可维护） |
| Banner 管理 | 卡片式列表（缩略图预览）；新建/编辑弹窗（传图、标题、副标题、链接、排序）；拖拽或上下移排序；上架/下架开关；删除二次确认 |
| 新闻管理 | 表格列表（标题/分类/状态/发布时间，支持标题搜索、状态筛选、分页）；编辑器页（标题、摘要、封面图、分类、富文本正文、发布时间、保存草稿/直接发布）；列表行内快捷发布/撤回/删除 |
| 酒店管理 | 表格列表（名称/品牌/城市/区域/状态，支持筛选）；编辑页（基本信息 + 主图上传 + 6 张网格图上传 + 设施勾选）；上架/隐藏开关 |
| 修改密码 | 旧密码 + 新密码（强度校验） |

交互细节遵循运营习惯：所有删除均需二次确认；所有表单均有必填校验与保存成功反馈；图片上传带预览与裁剪前提示（建议尺寸直接写在表单上）。

## 7. 官网前端改造与数据迁移

### 7.1 前端改造（改动小、可灰度）

1. 新增 `src/lib/api.ts`：封装 `fetchBanners() / fetchNews() / fetchHotels()`。
2. 三个消费点改为运行时取数：
   - 首页 Banner 区
   - 新闻页（`NewsPage`，替换 `EXTENDED_NEWS_LIST`）
   - 酒店名录页（`HotelDirectoryPage`，替换 `HOTEL_DIRECTORY_LIST`）
3. 每个区块加加载骨架屏与失败兜底（失败时静默降级为代码内置的最后一份静态数据，保证官网永远可打开）。
4. 类型直接从现有 `HotelShowcaseItem` / `DetailedNewsArticle` 平移到 `src/lib/types.ts`，前后端共享。
5. **咨询表单接 `/api/leads`**：合作加盟页表单当前仅前端假提交，改为真实落库；提交时附带 source_path / referrer / UTM；成功后保留现有"提交成功"动效。
6. **全站访问埋点**：`App.tsx` 视图切换时 `navigator.sendBeacon` 上报 `/api/track`（携带 path / title / referrer / visitor_id；`/admin` 不上报）；visitor_id 首次访问时生成随机串存 localStorage。

### 7.2 数据迁移（一次性）

- 编写 `scripts/seed.ts`：读取现有 `EXTENDED_NEWS_LIST`、`HOTEL_DIRECTORY_LIST`、首页 banner 硬编码数据，转成 SQL 插入。
- 其中引用的 unsplash 外链图片：迁移脚本统一下载 → 转 WebP → 存入 `uploads/`，数据库只存本地路径（避免外链失效、加载慢）。
- 首次启动容器时若数据库为空，自动执行种子导入。

## 8. Sealos 部署方案

### 8.1 构建（多阶段 Dockerfile，一个镜像搞定）

```
阶段1: node:22-alpine → 构建官网前端（vite build → dist）
阶段2: node:22-alpine → 构建管理后台（vite build → dist-admin）
阶段3: node:22-alpine → 编译后端（tsc / tsdown → server/dist）
阶段4: 运行时 → 拷贝三份产物 + node_modules（仅生产依赖）
启动: node server/dist/index.js（监听 3000）
```

### 8.2 Sealos 应用启动器配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 镜像 | 自构建镜像（或接 Sealos DevBox 源码构建） | |
| 实例数 | **固定 1** | SQLite + 本地持久卷不支持多副本，无需多副本 |
| CPU / 内存 | 0.5 核 / 512Mi（可随流量上调） | 内容站绰绰有余 |
| 持久卷 | 1Gi 挂载到 `/app/data` | 存 SQLite 文件 + uploads 图片 |
| 端口 | 3000 | |
| 公网访问 | 开启，绑定自有域名 | Sealos 自动签发 HTTPS 证书 |

### 8.3 备份

- 数据全部集中在 `/app/data`（一个 .db 文件 + 图片目录）。
- Sealos 持久卷支持快照；另加一个 Sealos 定时任务（CronJob）每日把 `/app/data` 打包上传对象存储/或异地，保留 7 天，成本可忽略。

## 9. 安全设计

- 密码 bcrypt（cost 12）哈希存储，永不落明文。
- JWT 走 httpOnly + Secure + SameSite=Lax Cookie，前端 JS 读不到，防 XSS 窃取；管理接口校验 Origin/Referer 头防 CSRF。
- 登录接口限流 + 失败锁定。
- 所有写接口 Zod 校验入参，SQL 全走参数化（Drizzle），杜绝注入。
- 上传白名单（jpg/png/webp）、大小限制、sharp 重编码剥离 EXIF 与恶意内容。
- 管理接口路径仅校验会话，不做 obscurity 依赖；`/admin` 静态页本身无敏感数据，数据全部走鉴权 API。
- Helmet 安全头；HTTPS 由 Sealos 网关强制。
